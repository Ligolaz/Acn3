# Мініпроєкт

## Тезисно що було зроблено

- Розробка програми-обгортки для контролю споживання ресурсів іншими процесами
- Використання системних викликів **getrlimit** та **setrlimit** для керування лімітами
- Реалізація механізму запуску сторонніх програм через **fork** та **execvp**
- Відстеження стану дочірнього процесу
- Тестування обмежень часу процесора, оперативної пам'яті та файлових дескрипторів

## Програмні вимоги

- Середовище запуску - термінал Linux (Ubuntu)
- Компілятор - GCC

## Збірка та запуск

### Обмежувач системних ресурсів (Завдання варіанту 4)

Розробити програму, яка запускає інший процес із заданими обмеженнями: максимальний час CPU, максимальний розмір пам’яті або кількість відкритих файлів.
Після перевищення ліміту програма має завершитися або отримати відповідний сигнал.
Бажано використати: setrlimit(), getrlimit(), fork(), exec().

### Реалізація

Програма реалізована за принципом монітора. За допомогою системного виклику fork() створюється копія процесу.
У дочірньому процесі, до моменту запуску цільової команди, встановлюються задані обмеження через функцію setrlimit().
Після цього код дитини повністю замінюється цільовою програмою через виклик execvp().

Батьківський процес при цьому залишається в режимі очікування через системний виклик waitpid().
Він відстежує завершення роботи дитини та аналізує статус її виходу: чи програма завершилася сама, чи була вбита ядром через порушення лімітів.
Службові повідомлення виводяться у потік stderr, щоб не змішуватися з результатом роботи самої програми.

### Використані системні виклики

- getrlimit()/setrlimit() - отримання та встановлення лімітів ресурсів;
- fork() - створення копії процесу;
- execvp() - заміна коду поточного процесу іншою програмою;
- waitpid() - очікування завершення дочірнього процесу;
- strsignal() - перетворення номера системного сигналу у зрозумілий текст.

### 1. Тестування ліміту часу CPU

Для тесту було використано команду yes, яка створює нескінченний цикл і максимально навантажує процесор.
При встановленні ліміту в 1 секунду, ядро ОС примусово зупиняє процес, як тільки він вичерпує свій час.
Така ситуація вважається некоректним завершенням, тому батьківський процес за допомогою системних макросів відловлює момент загибелі дитини.
Помилка обробляється через перехоплення сигналу, що дозволяє програмі не просто вилетіти, а вивести чітке повідомлення про причину зупинки:
```
user@user:~/project$ ./1 cpu 1 yes > /dev/null

(Parent) Child killed by signal: 9 (Killed)
```

### 2. Тестування ліміту відкритих файлів

Програмі ls було встановлено ліміт у 3 файлові дескриптори.
Оскільки для запуску утиліти та завантаження її системних бібліотек потрібно відкрити значно більше файлів, система заблокувала виконання ще на старті.
У цьому випадку некоректне завершення стається через неможливість отримати доступ до ресурсів файлової системи.
Програма обробляє це, аналізуючи код виходу, який повертає ОС, і повідомляє користувачу, що виконання було перервано через брак вільних дескрипторів
При встановленні ліміту у 7 файлів програма відпрацювала успішно:
```
user@user:~/project$ ./1 files 3 ls
ls: error while loading shared libraries: libselinux.so.1: cannot open shared object file: Error 24

(Parent) Child exited with code: 127
user@user:~/project$ ./1 files 7 ls
1  1.c

(Parent) Child exited with code: 0
```

### 3. Тестування ліміту пам'яті

Встановлено обмеження адресного простору у 10мб для python3.
Цього виявилося замало для мапування системної бібліотеки libc, тому ядро заблокувало мапування сегментів.
Некоректне завершення тут проявляється як системний збій на етапі запуску, про що програма дізнається через код помилки 127.
Батьківський процес відстежує цей статус через функцію очікування, що дозволяє зафіксувати невдачу при виділенні пам’яті. При 510мб все спрацювало коректно:
```
user@user:~/project$ ./1 mem 10485760 python3
python3: error while loading shared libraries: libc.so.6: failed to map segment from shared object

(Parent) Child exited with code: 127
user@user:~/project$ ./1 mem 510485760 python3
Python 3.12.3 (main, Mar  3 2026, 12:15:18) [GCC 13.3.0] on linux
Type "help", "copyright", "credits" or "license" for more information.

exit()

(Parent) Child exited with code: 0
```

## Висновки

У роботі було досліджено підсистему керування ресурсами Ядра ОС.
З точки зору системного програмування, було продемонстровано створення ізольованого середовища для програм за допомогою викликів fork та execvp.
Це дозволило на практиці побачити, як батьківський процес може контролювати ресурси дочірніх процесів, напряму взаємодіючи з ресурсами системи.

Роботу було зроблено на лінуксі, оскільки ця система надає зручний інтерфейс для налаштування лімітів через механізм setrlimit.
Це критично важливо для стабільності всієї ОС, щоб одна зависла програма не змогла забрати собі весь процесор чи пам'ять.
Було дотримано стандартів POSIX щодо використання сигналів та дескрипторів, завдяки чому програма-контролер чітко розпізнає, через що саме помер процес - через брак пам'яті чи перевищення часу.

Окрему увагу було приділено роботі з пам'яттю.
Було з'ясовано, що навіть для запуску найпростіших утиліт системі потрібно виділити чималий віртуальний адресний простір під бібліотеки.
Також використання потоку stderr замість стандартного буфера виводу дозволило бачити системні повідомлення та причини зупинки навіть тоді,
коли основний результат роботи програми було приховано або перенаправлено для ігнорування.
