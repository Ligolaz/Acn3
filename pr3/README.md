# Практична робота №3

## Тезисно що було зроблено

- Налаштування середовища **Docker** та робота з контейнерами в привілейованому та звичайному режимах
- Дослідження системних лімітів (**ulimit**) на кількість відкритих файлів, розмір файлів, час процесора та розмір стека
- Написання програм на **C**, що демонструють досягнення цих лімітів та обробку відповідних системних сигналів - **SIGXFSZ** та **SIGXCPU**
- Виконання стрес-тесту для перевірки максимальної кількості процесів

## Програмні вимоги

- Середовище запуску - Ubuntu, контейнер у Docker
- Компілятор - GCC
- Утиліти - ulimit, perf

## Збірка та запуск

### 1. Ліміти ulimit (Завдання 1)

Було проведено експеримент зі зміною ліміту на кількість відкритих файлів у двох режимах: звичайному та привілейованому **--privileged**

**Непривілейований режим:**
Спроба підняти ліміт вище жорсткого значення (Hard Limit) призвела до помилки:
```
root@3e9e4313bf99:/# ulimit -n 3001
bash: ulimit: open files: cannot modify limit: Operation not permitted
```
**Привілейований режим (root):**

З прапорцем --privileged зміна ліміту пройшла успішно, оскільки контейнер отримав доступ до параметрів ядра:
```
root@60b306d0eb96:/# ulimit -n 3001
root@60b306d0eb96:/# ulimit -n
3001
```

### 2. Кількість відкритих файлів (Завдання 2)

Програма намагається відкрити файл зі назвою **empty.txt** нескінченну кількість разів. При досягненні ліміту **ulimit -n** програма повідомляє про кількість успішно відкритих файлів:
```
root@60b306d0eb96:/# ulimit -n 100
root@60b306d0eb96:/# ./2
Limit reached. Opened 97 files
root@60b306d0eb96:/# ulimit -n 1000
root@60b306d0eb96:/# ./2
Limit reached. Opened 997 files
```

### 3. Обмеження розміру файлу (Завдання 3)

Програма записує результати кидків кубика у файл **rolls.txt**. Встановлено обробник сигналу (функція limit_reached()) **SIGXFSZ**, що спрацьовує при перевищенні ліміту розміру файлу **ulimit -f**:
```
root@60b306d0eb96:/# ulimit -f 1
root@60b306d0eb96:/# ./3
Limit was reached so imma stop
```
### 4. Обмеження часу CPU (Завдання 4)

Програма генерує випадкові числа для лотереї та виводить їх на екран. Оскільки сучасні процесори виконують цю операцію миттєво, для демонстрації роботи ліміту **ulimit -t 1** присутній цикл, який продовжує генерувати лотерейні комбінації у фоновому режимі, що створює навантаження на процесор, доки система не надішле сигнал SIGXCPU, або SIGKILL, якщо сигнал не оброблено вчасно:
```
root@60b306d0eb96:/# gcc 4.c -o 4
root@60b306d0eb96:/# ulimit -t 1        
root@60b306d0eb96:/# ./4
7 із 49: 42 15 3 49 22 8 11 
6 із 36: 34 12 5 28 1 19 
Simulating massive lottery calculations to hit CPU limit...

CPU is down. (SIGXCPU)
```
### 5. Копіювання файлів з обмеженням (Завдання 5)

Програма копіює вміст одного файлу в інший. Реалізовано перевірку аргументів та доступності файлів. При перевищенні ліміту розміру вихідного файлу спрацьовує захист. Ефект ліміту можно побачити при порівнянні вмісту файлів **from.txt** та **to.txt** - файл to.txt має в собі контент записаний починаючи з початку файлу і аж до спрацювання захисту. Запуск:
```
root@60b306d0eb96:/# ./5 from.txt to.txt
Limit was reached
```
### 6. Переповнення стека (Завдання 6)

Рекурсивна програма викликає сама себе, заповнюючи стек. При досягненні ліміту `ulimit -s` відбувається помилка сегментації (Segmentation fault), яку неможливо перехопити звичайним сигналом:
```
root@60b306d0eb96:/# ulimit -s 1000
root@60b306d0eb96:/# ./6 100000
Recursing 100000 times...
Segmentation fault (core dumped)
```

### 7. Тест макс. кількості процесів (Завдання варіанту 4)

Програма створює дочірні процеси у нескінченному циклі. Коли досягається ліміт **ulimit -u**, системний виклик **fork()** повертає помилку, і програма повідомляє загальну кількість створених процесів. Запуск із лімітом 200 процесів:
```
root@60b306d0eb96:/# ulimit -u 200
root@60b306d0eb96:/# ./7
Stress testing process limit (ulimit -u)...
...
Created 6950 processes...
Created 7000 processes...

Limit reached so fork failed.
Successfully created 7010 child processes.
The rest of the limit is likely taken by system processes.
```
## Висновки

У роботі було практично досліджено, як саме Linux обмежує ресурси для програм. За допомогою Docker було перевірено ситуації, коли процесу бракує пам'яті, часу процесора або можливості відкрити новий файл.

Було проаналізовано роботу головної частини ОС - Ядра. Саме воно виступає контролером, який через налаштування ulimit слідкує за тим, щоб одна програма не забрала всі ресурси (пам'ять, процесорний час) і не порушила стабільність роботи інших процесів.

Також було розібрано механізм Сигналів (стандарт POSIX). Коли програма намагалася порушити встановлений ліміт (наприклад, створити зайвий процес через fork), ядро блокувало цю дію і повідомляло про помилку спеціальним сигналом (наприклад SIGXCPU). Це показало, як програма взаємодіє із системними викликами.

Окрему увагу було приділено буферизації. З'ясувалося, що при записі у файл дані спершу накопичуються у буфері програми. Перевірка ліміту ядром відбувається не в момент генерації даних, а лише коли цей буфер фактично "скидається" на диск.

Виконання роботи у середовищі Linux із контейнером у Docker підтвердило ефективність механізмів ізоляції ресурсів. Розуміння цих принципів дозволяє розробляти програмне забезпечення, здатне коректно обробляти дефіцит ресурсів без аварійного завершення роботи системи.
