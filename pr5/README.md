- Виявлення некоректного звільнення пам'яті та аналіз звіту про помилки

## Збірка та запуск

### Подвійне звільнення пам'яті (Варіант 4)

Написано програму, у якій виділяється невелика ділянка пам'яті за допомогою функції malloc. Оскільки розмір блоку є малим, бібліотека glibc використовує механізм оптимізації tcache (thread local cache).
Спочатку відбувається перший виклик free(ptr), після чого адреса пам'яті додається у структуру tcache для швидкого повторного використання.
Далі виконується другий виклик free(ptr), який намагається звільнити ту ж саму ділянку пам'яті. Це призводить до heap corruption, тобто програма змінює дані, що належать алокатору

Запуск програми з valgrind допомагає переконатися, що помилка виникає саме через повторне звільнення вже звільненого блоку, та дозволяє виявити місце помилки ще до падіння програми

Для компіляції використано прапорці **-g** (для додавання відлагоджувальної інформації) та **-O0** (для вимкнення оптимізації компілятора, щоб зберегти логіку помилки):

## Висновки

У роботі було розібрано, як операційна система керує своїм одним із головних ресурсів - пам'яттю. З точки зору системного програмування, керування ресурсами здійснювалося вручну: виконувалися запити на отримання пам'яті з Heap-у та її повернення.

Виконання проводилося саме на Linux, оскільки тут використовується специфічний механізм tcache. По суті, це буфер, де система тимчасово зберігає дрібні шматки звільненої пам'яті, щоб прискорити роботу.
Було змодельовано ситуацію, коли цей буфер ламається через помилку Double Free, що є критичним для стабільності системи.

Для виявлення проблеми було використано Valgrind, оскільки у віртуальній пам'яті такі помилки часто залишаються непомітними.

Це дозволило чітко побачити порушення правил роботи з пам'яттю, що є необхідним для створення надійних програм, які відповідають стандартам загальних правил для систем типу Unix - POSIX.
