# Практична робота №4

## Тезисно що було зроблено

- Дослідження максимального обсягу пам'яті для **malloc(3)** на 32-х та 64-х бітних системах
- Аналіз поведінки `**malloc** при передачі від'ємних значень (Integer Overflow)
- Дослідження граничних випадків: **malloc(0)**, **realloc** з **NULL** та **0**
- Аналіз викликів через **ltrace**
- Перевірка повторного використання адрес пам'яті після **free()**

## Програмні вимоги

- Середовище запуску - термінал Linux (Ubuntu)
- Компілятор - GCC (з підтримкою multilib для 32-біт)
- Утиліта - ltrace

## Збірка та запуск

### 1. Скільки пам’яті може виділити malloc (Завдання 1)

Програма визначає розмір **size_t** та теоретичний максимум для алокації. На 64-бітній системі це 16 Ексабайт, на 32-бітній — 4 ГБ

**Компіляція та запуск (64-біт):**
```
./1_64
Bits in size_t: 64
Max size_t (2^64): 18446744073709551615 bytes
malloc(3) can allocate 16 EB or 18446744073709551615 B max
```
**Компіляція та запуск (32-біт):**
```
./1_32
Bits in size_t: 32
Max size_t (2^32): 4294967295 bytes
malloc(3) can allocate 0 EB or 4294967295 B max
```
### 2. Від'ємний аргумент та переповнення (Завдання 2)

При передачі від'ємного числа int у malloc, воно конвертується у величезне беззнакове число size_t (через особливості представлення чисел в пам'яті), що призводить до неможливості виділення пам'яті

**Запуск (64-біт):**
```
./2_64
xa: 100, xb: 200
num: 20000
num_sizet = 20000
Allocated 20000 bytes

xa: 2147483647, xb: 2
num: -2
num_sizet = 18446744073709551614
Didn't allocate 18446744073709551614 bytes
```
**Запуск (32-біт):**
```
./2_32
...
xa: 2147483647, xb: 2
num: -2
num_sizet = 4294967294
Didn't allocate 4294967294 bytes
```
### 3. malloc(0) (Завдання 3)

malloc(0) може повернути **NULL** або **унікальний вказівник**. На цій системі повертається вказівник, який можна безпечно передати у free().

**Запуск із ltrace:**
```
ltrace ./3
malloc(0) = 0x609baac7b2a0
printf("Returned pointer: %p\n", 0x609baac7b2a0Returned pointer: 0x609baac7b2a0
) = 33
free(0x609baac7b2a0) = <void>
+++ exited (status 0) +++
```
### 4. Помилка Use After Free (Завдання 4)

Демонстрація логічної помилки, коли перевірка **if (!ptr)** спрацьовує неправильно, бо вказівник не було занулено після **free**. У проблемній програмі пам'ять виділяється лише один раз, далі йде запис у звільнену пам'ять, а у виправленій після **ptr = NULL** пам'ять коректно виділяється щоразу

**Проблемна програма:**
./4_1
```
ptr: 0x55b5facd82a0
```
**Виправлена програма:**
```
./4_2

ptr: 0x634f721bf2a0

ptr: 0x634f721bf2a0

tr: 0x634f721bf2a0
```
### 5. Невдалий realloc (Завдання 5)

Якщо **realloc** не може виділити пам'ять (наприклад, запитано **size_t - 1**), він повертає **NULL**, але старий вказівник залишається валідним

**Запуск:**
```
./5
Allocated 10 bytes
ptr: 0x5e60a43682a0
Didn't realloc to ptr1
ptr: 0x5e60a43682a0
```
### 6. realloc з NULL або 0 (Завдання 6)

**realloc(NULL, size)** працює як **malloc(size)**. **realloc(ptr, 0)** працює як **free(ptr)** і повертає **NULL**

**Запуск:**
```
./6
Reallocated ptr with NULL: 0x5f2f5dee32a0
realloc with 0 size ptr1 is NULL
```
### 7. Використання reallocarray (Завдання 7)

Функція **reallocarray** безпечніша, бо перевіряє переповнення при множенні кількості елементів на їх розмір

**Запуск із ltrace:**
```
ltrace ./7
calloc(1000, 8) = 0x556546e4c2a0
printf("Callocated ptr: %p\n", 0x556546e4c2a0Callocated ptr: 0x556546e4c2a0
) = 31
reallocarray(0x556546e4c2a0, 500, 8, 0) = 0x556546e4c2a0
printf("Reallocarray'd newptr: %p\n", 0x556546e4c2a0Reallocarray'd newptr: 0x556546e4c2a0
) = 38
free(0x556546e4c2a0) = <void>
+++ exited (status 0) +++
```
### 8. Перевикористання пам'яті (Завдання варіанту 4)

Програма перевіряє, чи повертає malloc ту саму адресу після free. Результат показує, що для малих блоків (32 байти) система активно перевикористовує звільнену пам'ять (адреси збігаються 4 з 4 разів). Для великих блоків (1 МБ) також спостерігається перевикористання, хоча іноді адреса може змінюватись (адреси збігаються на 75%).

**Запуск:**

```
    ptr: 0x59dd1c4566b0 (REUSED)

    ptr: 0x59dd1c4566b0 (REUSED)

    ptr: 0x59dd1c4566b0 (REUSED)

    ptr: 0x59dd1c4566b0 (REUSED)
    Reused: 4 times

Large blocks (1 MB)

    ptr: 0x7394d045a010

    ptr: 0x59dd1c4566e0

    ptr: 0x59dd1c4566e0 (REUSED)

    ptr: 0x59dd1c4566e0 (REUSED)

```
## Висновки

Було досліджено механізми керування динамічною пам'яттю в мові C. Перевірено поведінку функцій **malloc**, **free**, **realloc** у граничних випадках.

Продемонстровано як виникає вразливість **Use-After-Free** та як переповнення цілих чисел при розрахунку розміру пам'яті може призвести до непередбачуваних наслідків. Використання **reallocarray** показано як безпечнішу альтернативу звичайному множенню аргументів.

Також було підтверджено, що алокатор пам'яті в Linux (glibc) оптимізований для швидкодії: він намагається перевикористовувати нещодавно звільнені блоки пам'яті, замість того щоб щоразу створювати нові.
