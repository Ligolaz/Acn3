# Практична робота №8

## Тезисно що було зроблено

- Дослідження механізму часткового запису **partial write** у неблокуючі канали
- Аналіз роботи системного виклику **lseek** для позиціонування у файлі
- Тестування швидкодії алгоритму **qsort** на масивах різного об'єму
- Вивчення результатів системного виклику **fork()** для ідентифікації процесів
- Експериментальне визначення умов виникнення часткового зчитування **partial read**

## Програмні вимоги

- Середовище запуску - термінал Linux (Ubuntu)
- Компілятор - GCC

## Збірка та запуск

### 1. Частковий запис (Завдання 1)

Демонстрація ситуації, коли write записує менше байтів, ніж було запрошено. У неблокуючому режимі запис у трубу обмежився розміром системного буфера (64 КБ), хоча запит був на 100 КБ:
```
user@user:~/lab8$ ./1
Requested: 100000, Written: 65536
```

### 2. Позиціонування та читання (Завдання 2)

Перевірка роботи lseek та read у певній послідовності. Програма підтверджує, що після зміщення вказівника на 3-й байт, зчитування повертає очікувані дані з середини масиву:
```
user@user:~/lab8$ ./2
Buff contains: 2 3 3 7 
```

### 3. Аналіз швидкодії qsort (Завдання 3)

Замір часу виконання сортування для масивів на 100 тисяч та 1 мільйон елементів. Результат показує зростання часу обробки пропорційно до об'єму вхідних даних:
```
user@user:~/lab8$ ./3
Small (n=100000): 0.023 sec
Large (n=1000000): 0.279 sec
```

### 4. Результати fork (Завдання 4)

Демонстрація значень, які повертає fork() після успішного створення процесу. Батьківський процес отримує PID дитини, а дочірній - нуль, що дозволяє програмі розділяти логіку виконання:
```
user@user:~/lab8$ ./4
(Parent proc) Child ID: 3050
(Child proc) PID: 0
```

### 5. Умови часткового read (Завдання варіанту 4)

Написано програму для демонстрації ситуації, коли read() повертає менше байтів, ніж було запрошено.
Для тесту використано анонімний канал pipe, у який було записано лише 5 байтів даних. При спробі зчитати з нього 100 байтів, система повернула лише 5 наявних, не чекаючи повного заповнення запиту.
Це наочно підтверджує, що системний виклик повертає стільки даних, скільки фактично доступно в ресурсі на момент звернення:
```
user@user:~/lab8$ ./5
Requested: 100 bytes from pipe
Actually read: 5 bytes
Reason: Pipe had only 5 bytes available at the moment
```

## Висновки

У ході роботи було досліджено низькорівневу взаємодію програми з ядром ОС через системні виклики вводу/виводу. Було проаналізовано роботу підсистем **керування процесами** та **файлової системи**, зокрема механізмів передачі даних через дескриптори.

Виконання завдань продемонструвало важливість перевірки результатів системних викликів, оскільки вони залежать від стану системних ресурсів, наприклад, розміру буферів у пам'яті ядра.
Це є критичним для написання надійного системного коду, що відповідає стандартам POSIX та коректно обробляє часткові операції зчитування та запису.
